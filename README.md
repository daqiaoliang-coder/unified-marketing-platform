# Unified Marketing Platform

> 统一营销平台：面向电商交易的统一营销与优惠底层体系，覆盖营销玩法接入、统一出价、优惠计算编排、优惠资源管理及订单生命周期中的营销业务流转。

本仓库包含基于项目经历整理的架构说明，以及使用 Java 21 / Spring Boot / JDBC 实现的可运行参考系统。实现是独立编写的演示版本，不包含原业务系统源码；以下明确区分原始业务描述与本仓库采用的具体规则，不应直接作为生产交易系统部署。

## 1. 平台定位

统一营销平台承载电商营销体系，为不同营销玩法提供统一的优惠底层能力，连接商品展示、交易询价、下单及订单后续流转。

- **商品详情页**：提供统一出价接口，统一承接营销优惠的价格展示需求。
- **交易询价**：完成优惠计算、活动组合与价格处理。
- **交易下单**：承接优惠快照持久化、优惠资源扣减与锁定。
- **订单流转**：通过优惠快照衔接同步回滚与异步营销业务处理。

## 2. 业务能力

| 业务目标 | 营销玩法 |
| --- | --- |
| 拉新 | 秒杀、拼团 |
| 复购 | 复购券、定向优惠 |
| 提升客单价 | 优惠套餐、满减 |
| 促进成交 | 限时折扣、满减及其他优惠工具 |

这些玩法共享优惠计算与交易处理能力，而不是各自维护完整的交易优惠链路。

## 3. 两大核心接口

| 接口 | 核心职责 | 关键机制 |
| --- | --- | --- |
| **读接口：优惠计算** | 计算订单可用优惠及其组合，处理价格与金额分配 | 计算编排、叠加、排他、排序、均摊、各方分润 |
| **写接口：优惠执行** | 将优惠计算结果衔接到下单与订单生命周期 | 优惠快照、资源扣减与锁定、分布式事务、同步回滚与异步流转 |

读接口关注“优惠如何计算与组合”，写接口关注“优惠如何执行，以及订单变化后如何继续处理或回滚”。

## 4. 读接口：优惠计算与编排

### 4.1 核心构成

| 构成 | 作用 |
| --- | --- |
| 查询计划、过滤器 | 组织优惠相关数据查询，并过滤候选数据或活动 |
| Callback 回调层、Callable 取数 | 衔接优惠计算所需的数据与回调处理 |
| 优惠计算编排 | 组织活动挂载、组合生成、叠加与排他、排序及金额处理 |
| 插件、插件过滤器 | 过滤参与执行的优惠插件，并承载具体优惠计算 |
| 优惠工具执行引擎 | 根据条件元数据与配置元数据，产出结果元数据 |

执行引擎以元数据描述优惠工具的计算输入与输出：

```text
条件元数据 + 配置元数据 → 结果元数据
```

### 4.2 主计算链路

```text
查询计划 / 过滤器 / Callback 回调层
                  ↓
           从 Callable 中取数
                  ↓
     将可能参与计算的优惠活动挂载到订单
                  ↓
          针对每个订单计算叠加组合
       ├─ 自叠加
       ├─ 优惠活动类型叠加
       └─ 叠加 / 排他规则约束
                  ↓
       针对每个叠加组合计算笛卡尔积
                  ↓
     将笛卡尔积中的每个元素作为优惠组合
                  ↓
      每个优惠组合经插件过滤与插件计算
                  ↓
         更新子订单实付款，继续计算
                  ↓
        汇总计算结果与金额分配结果
```

### 4.3 优惠组合计算

优惠计算不只是执行单个活动，而是处理多个活动在订单上的组合关系：

1. **挂载候选活动**：将可能适用的优惠活动关联到订单。
2. **计算叠加关系**：区分活动自叠加与不同优惠活动类型之间的叠加，并处理排他约束。
3. **生成候选组合**：针对每个叠加组合计算笛卡尔积，将其中每个元素展开为具体优惠组合。
4. **执行组合计算**：通过插件对每个优惠组合进行优惠计算。
5. **处理排序与金额分配**：在计算编排中处理排序、优惠均摊及各方分润。

排序、均摊、分润属于整体计算能力；这里不将其限定为所有玩法都完全一致的固定执行顺序。

### 4.4 子订单与主订单的计价关系

订单之间的优惠计算存在基准价依赖：每计算下一个订单前，需要更新子订单实付款，用于后续主订单基准价计算。

```text
子订单优惠计算 → 更新子订单实付款 → 主订单基准价计算 → 后续优惠计算
```

这一关系意味着计算编排必须关注订单层级与执行顺序，不能将各订单的优惠计算简单视为彼此独立。

## 5. 写接口：快照、资源与分布式事务

### 5.1 下单同步处理

订单下单时，先保存优惠快照，再通过 `dealPromotionAfter` 执行后续优惠处理，承接优惠资源扣减等同步操作；优惠资源锁定也属于平台写侧能力。

```text
交易下单 → 保存优惠快照 → dealPromotionAfter → 同步优惠处理 / 资源扣减
```

优惠快照为后续订单流转与回滚提供优惠处理上下文。

### 5.2 订单流转后的异步处理

订单状态流转后，通过异步消息与优惠快照驱动营销业务：先查询快照，再调用 `dealPromotionAfter` 进行相应处理。

```text
订单流转 → 异步消息 → 查询优惠快照 → dealPromotionAfter
                                             ├─ 优惠回滚
                                             ├─ 满送
                                             └─ 赠金币等业务
```

### 5.3 TCC 同步回滚

分布式事务场景下，TCC 同步回滚同样基于优惠快照恢复处理上下文，再进入 `dealPromotionAfter` 执行回滚。

```text
TCC 同步回滚 → 查询优惠快照 → dealPromotionAfter → 优惠回滚处理
```

### 5.4 写侧处理路径汇总

| 触发场景 | 快照操作 | 处理入口 | 业务职责 |
| --- | --- | --- | --- |
| 下单同步处理 | 先保存快照 | `dealPromotionAfter` | 同步优惠处理、优惠资源扣减 |
| 订单流转异步消息 | 先查询快照 | `dealPromotionAfter` | 优惠回滚、满送、赠金币等 |
| TCC 同步回滚 | 先查询快照 | `dealPromotionAfter` | 分布式事务中的同步优惠回滚 |

三条路径共享快照与处理入口，但触发时机和业务语义不同，不能将异步业务流转与 TCC 同步回滚混为同一条链路。

## 6. 核心设计要点

- **统一营销底座**：以共享的计算与写侧能力承接拉新、复购、客单价提升和促成交等营销需求。
- **优惠组合编排**：将叠加、排他和笛卡尔积组合计算纳入统一流程，处理多活动并存的复杂性。
- **插件化与元数据驱动**：由插件承载具体优惠计算，以条件元数据、配置元数据和结果元数据组织优惠工具执行。
- **订单层级感知**：将子订单实付款更新与主订单基准价计算纳入编排，保持计算依赖明确。
- **计算与执行职责分离**：读侧负责优惠与金额计算，写侧负责快照、资源处理及订单后续流转。
- **快照驱动的生命周期处理**：以优惠快照连接下单执行、异步营销业务与 TCC 同步回滚。

## 7. Java 参考实现

### 技术与结构

- Java 21+、Maven 3.9+、Spring Boot 3.5.7。
- Spring MVC 提供 JSON HTTP 接口，Jakarta Validation 校验外部输入。
- JDBC + H2 文件数据库保存活动、资源、快照、事件与权益，重启保留数据。
- JUnit 5 / AssertJ / MockMvc 验证金额、组合、事务、并发和 HTTP 行为。

```text
src/main/java/com/example/marketing/
├── domain/        活动元数据、订单输入、报价与事务模型
├── engine/        组合搜索、优惠插件、按分均摊
├── service/       查询计划、计算编排、TCC、订单事件与权益
├── persistence/   JDBC 持久化
└── api/           HTTP 接口与错误映射
```

### 已实现能力与明确规则

| 能力 | 本仓库实现规则 |
| --- | --- |
| 查询计划与 Callback | 以数据源 Callback 生成 Callable 查询计划，默认从 JDBC 活动目录取数；候选再经时间、人群、SKU 和门槛过滤 |
| 优惠工具 | 固定减额、比例减额、指定单件价格三种插件；玩法类型与计算公式分离 |
| 叠加与排他 | 同类型要求双方允许自叠加；异类型要求双方互相允许；同一非空排他组不能并用 |
| 笛卡尔积 | 按活动类型生成可选子集，再展开跨类型组合并剪枝；包含不使用优惠的空组合 |
| 订单层级 | 子订单 ORDER 优惠先计算，更新实付款后计算购物车 CART 优惠；搜索完整组合，避免局部最优造成全局损失 |
| 跨层兼容 | 不同子订单独立；CART 活动与所有已应用的 ORDER 活动进行兼容校验，采用保守的跨层排他规则 |
| 执行与选择顺序 | priority 升序、活动 id 稳定排序；选择最终实付最低的组合；同价时依次比较金币多、赠品多、活动数少和稳定活动标识 |
| 金额 | 全部 long，单位为分；比例减额以基点表示，1000 表示减 10%；乘除中间值避免溢出，按最大余数法处理均摊尾差 |
| 出资承担 | fundingBps 必须合计 10000；计算商家/平台等各方承担的优惠金额，不冒充实际分账结算 |
| 资源 | available / reserved / consumed 非负，三者之和恒等于 total；一个被应用的活动每次消耗其 resourceUnits |
| Try / Confirm / Cancel | Try 写快照并预占，Confirm 将预占转为消耗，Cancel 释放预占；空回滚留下终态记录阻止悬挂 Try |
| 同步下单 | `/api/orders` 在一个本地事务中完成 Try + Confirm，先快照后资源处理 |
| 订单事件 | 持久化 inbox，定时读取并处理；权益/补偿与事件确认处于同一本地事务 |
| 幂等与补偿 | transactionId、cartId、eventId 和权益唯一键防重；订单取消可补偿已消耗资源并撤销权益，迟到支付事件不能重新发放 |
| 错误重试 | 失败记录入库，指数退避，最多 8 次后 FAILED；支持人工重新入队 |
| 快照隔离 | 后续确认、回滚和权益发放只读原优惠快照，不依赖已经修改的活动配置 |

以上为本仓库明确采用的参考规则，不表示原系统的未公开实现也是如此。每个计算范围最多 12 个有效候选，请求有 50000 次搜索预算，超限返回 `COMBINATION_LIMIT`，不静默返回未完成搜索的结果。

### 运行边界

- 默认仅监听 `127.0.0.1`，没有用户认证和商家租户权限，**不要直接暴露到公网**。
- 接口面向可信交易调用方；`customerId`、商品价格和用户资格需要真实业务的上游校验，不能直接信任终端用户提交的价格。
- 秒杀、拼团、券、定向优惠等是可配置的活动类型；未实现拼团成团、用户领券账户、支付网关、实物履约和实际金币钱包。满送、赠金币在这里落为可撤销的权益账本。
- TCC 是本平台资源参与者的实现，不包含外部分布式事务协调器、超时回收或跨服务一致性协议。调用方必须最终执行 Confirm 或 Cancel。
- 已 Confirm 的事务不能走 TCC Cancel；业务取消通过 `CANCELLED` 订单事件补偿。不包含部分退款。
- 活动资源在写侧原子检查，询价不预占资源；有价不代表有库存。
- H2 文件库是本机参考存储；用数据库互斥行串行化写操作以保证演示一致性，不宣称高并发性能。生产化需替换存储、锁粒度、鉴权、价格来源及消息设施。
- 金额门槛基于当前剩余应付金额；活动时间采用左闭右开 `[startsAt, endsAt)`；空 SKU / customer 集合表示不限。
- 同一 cartId 只允许一笔事务。取消后需使用新的 cartId、transactionId；这些终态记录不会被自动删除。

## 8. 本地运行

```bash
mvn test
mvn package
java -jar target/unified-marketing-platform-0.1.0-SNAPSHOT.jar
```

服务默认地址为 `http://127.0.0.1:8080`，文件数据库位于 `data/`。首次启动为空目录，不会自动创建活动或扣减资源。

```bash
curl http://127.0.0.1:8080/api/health

curl -X POST http://127.0.0.1:8080/api/resources \
  -H 'Content-Type: application/json' \
  -d '{"id":"coupon-stock","total":1000}'

curl -X PUT http://127.0.0.1:8080/api/promotions/coupon-20 \
  -H 'Content-Type: application/json' \
  --data-binary @examples/promotion.json

curl -X POST http://127.0.0.1:8080/api/quotes \
  -H 'Content-Type: application/json' \
  --data-binary @examples/cart.json
```

示例订单原价 `15000` 分，满减 `2000` 分，实付 `13000` 分；商家承担 `1600` 分、平台承担 `400` 分。报价不会扣减资源。

### TCC 与异步权益完整链路

```bash
curl -X POST http://127.0.0.1:8080/api/transactions/try \
  -H 'Content-Type: application/json' \
  --data-binary @examples/order.json

curl -X POST http://127.0.0.1:8080/api/transactions/tx-demo/confirm

curl -X POST http://127.0.0.1:8080/api/events \
  -H 'Content-Type: application/json' \
  -d '{"eventId":"paid-demo","transactionId":"tx-demo","type":"PAID"}'

curl http://127.0.0.1:8080/api/events/paid-demo
curl http://127.0.0.1:8080/api/transactions/tx-demo/rewards
curl http://127.0.0.1:8080/api/resources
```

事件返回 `202` 代表已持久化接收，不代表处理完成；默认每秒消费一次，查询状态达到 `PROCESSED` 后可看到 100 金币和 1 件赠品的权益记录。无需独立 Try/Confirm 时，可向 `/api/orders` 提交同一格式请求完成同步下单。

```bash
curl -X POST http://127.0.0.1:8080/api/events \
  -H 'Content-Type: application/json' \
  -d '{"eventId":"cancel-demo","transactionId":"tx-demo","type":"CANCELLED"}'

curl http://127.0.0.1:8080/api/events/cancel-demo
curl http://127.0.0.1:8080/api/transactions/tx-demo/rewards
```

取消处理完成后资源归还、权益变为 `REVOKED`。重复运行时请为新业务生成新的订单与事务标识；同一事件或事务可以使用原标识安全重试，但不能用同一标识提交不同内容。

## 9. HTTP 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/health` | 运行状态 |
| GET / PUT | `/api/promotions` / `/api/promotions/{id}` | 查看 / 配置活动 |
| GET / POST | `/api/resources` | 查看资源 / 创建资源池 |
| POST | `/api/quotes` | 详情出价与交易询价，单商品可构造单订单单行请求 |
| POST | `/api/orders` | 同步快照与资源扣减 |
| POST | `/api/transactions/try` | TCC Try，含 expectedPayable 重新计价校验 |
| POST | `/api/transactions/{id}/confirm` | TCC Confirm |
| POST | `/api/transactions/{id}/cancel` | TCC Cancel，支持空回滚 |
| GET | `/api/transactions/{id}` | 查询优惠快照和状态 |
| GET | `/api/transactions/{id}/rewards` | 查询金币与赠品权益 |
| POST | `/api/events` | 接收 PAID / CANCELLED 订单事件 |
| GET | `/api/events/{id}` | 查询消费状态与重试情况 |
| POST | `/api/events/{id}/retry` | FAILED 事件人工重试 |

错误响应统一为 `{"code":"...","message":"..."}`。常见错误：非法字段 `400`、对象不存在 `404`、价格变化/资源不足/幂等冲突/不合法状态迁移 `409`、组合搜索超限 `422`。
